# ローカルLLM活用アプリ 仕様書

> 2026-09-01 改訂。初版（構想時）を、実装完了後の「作られたもの」の仕様に書き直したもの。
> 設計方針を変えるときは、コードより先にこの3ファイル（`01_仕様書` / `02_調査結果` / `03_実行計画書`）を更新すること。

## 0. 設計思想（これを継いでほしい）

- **チャットではなくワークフロー。** ユーザー入力を受けてから、埋め込み → 検索 → プロンプト構成 → 生成、という複数ステップの関数呼び出しの連鎖として処理する。ノードUIではなく、コード上の非同期パイプライン。各ステップは独立・差し替え可能に保つ。
- **ローカル完結・Python不要。** フロントからバックまで TypeScript / Node.js。LLM は自宅PCの Ollama。ベクトルDBはアプリ内蔵（LanceDB）。管理対象のプロセスを増やさない。
- **軽量モデル前提で、役割ごとにモデルを分ける。** 1モデルに全部やらせない。応答生成・要約・埋め込みで別モデル。
- **長期記憶と文脈管理を主機能に据える。** チャット履歴を垂れ流さない。古い文脈は自動で要約に畳み、恒常的な事実は長期知識（RAG）へ移す。ユーザーが手動で緊急圧縮もできる。
- **遅さを、学びと手遊びの時間に変える。** GPUが非力で複数モデルをスワップするため生成は遅い（数十秒）。その待ち時間に、パイプラインの各処理を3Dで図解した「窓」を触って回せる。正確な図解で仕組みの理解が得られ、結果として体感待ち時間が短くなる——これがビジュアライゼーションの狙い。単なるローディング演出ではない。
- **壊れても止まらない。** Ollama停止・検索失敗・空応答・一過性エラーのいずれでもクラッシュせず、適切なメッセージを出して回復手段（管理画面の再起動など）へ導く。

## 1. 目的

Ollama 上の軽量ローカルLLMを使い、RAGによる長期知識の蓄積、KVキャッシュ／コンテキストの自動・手動管理、Ollamaサーバーの死活監視・再起動をGUIから行える、自宅PC常駐型の Next.js アプリを構築する。

## 2. 背景・前提

- 開発者は TypeScript 学習中。Python を使わず一気通貫で実装したい。
- 生成AI体験は既製チャットクライアント中心。コードベースのワークフロー構築は初挑戦（ノードベースの画像生成ツール経験のみ）。
- PCスペック制約により軽量パラメータ帯のモデルを前提。GPUは discrete Radeon RX Vega（VRAM 8GB、Ollama から Vulkan で利用）。
- Ollama は常時起動。Tailscale により外出先スマホからアクセスできるネットワークが構築済み。

## 3. システム全体構成

```
[スマホ / 外出先ブラウザ]
      │  (Tailscale・同一Tailnet内のみ)
      ▼
[自宅PC  <Tailscale ホスト名 / IP>]
 ├─ Node.js 24
 ├─ Next.js 16 アプリ（App Router / src/ / Turbopack）
 │    ├─ src/proxy.ts            共有パスワードによる全ルート保護
 │    ├─ /                        チャット / ワークフロー UI（可視化つき）
 │    ├─ /viz                     処理ビジュアライゼーション（単体）
 │    ├─ /admin                   管理画面
 │    ├─ /manual                  アプリ内説明書（設定値は実コードから読む）
 │    ├─ /login
 │    └─ /api/*                   chat(NDJSON) / conversation / knowledge /
 │                                ollama(health, restart) / status / auth
 ├─ Ollama（localhost:11434, 0.0.0.0 バインド）
 │    ├─ 応答生成  qwen3.5:9b
 │    ├─ 要約      qwen3.5:2b
 │    └─ 埋め込み  bge-m3
 ├─ LanceDB（data/lancedb/）           長期知識のベクトルストア
 └─ data/conversation.json             会話履歴＋ローリング要約
```

Next.js が司令塔。`/api/chat` は 1リクエストを NDJSON ストリームで返し、6ステージの進捗（実測値つき）を逐次送る。

## 4. 機能要件

### 4.1 ワークフロー実行

ユーザー入力に対し、以下を順に実行する。各ステージの開始・終了（所要ms・件数など）を NDJSON で流す。

| # | ステージ | 内容 |
|---|---|---|
| 1 | input | メッセージ受領・長さ計測（トークン分割はモデル側） |
| 2 | embed | 質問文を `bge-m3` で 1024次元ベクトル1本に |
| 3 | retrieve | 長期知識をコサイン距離で検索、`≤0.75` かつ上位3件 |
| 4 | prompt | 知識 → 過去の要約 → 直近の会話（最大24件）→ 質問、を1メッセージ列に |
| 5 | generate | `qwen3.5:9b` が自己回帰で応答生成 |
| 6 | persist / compact | 履歴保存 → 閾値超なら自動圧縮 |

各ステップは独立した非同期関数（`src/lib/` 配下）。テスト・差し替えが容易な構造を保つ。

### 4.2 長期知識 RAG

- 事実を埋め込みベクトルとして LanceDB（`data/lancedb/`）に保存。
- 投入経路は2つ：`manual`（ユーザーが知識パネルから登録）／ `auto`（文脈圧縮時に要約モデルが恒常的事実を最大5件抽出して自動保存）。
- 質問時に毎回検索し、ヒットは `system` メッセージとしてプロンプト先頭に注入（「関係なければ無視して」を添える）。
- 個別削除は持たない。消去は全消去のみ（知識パネル or 管理画面）。

### 4.3 コンテキスト／KVキャッシュ管理

- 会話マネージャー（`src/lib/conversation.ts`）が履歴配列とローリング要約を保持し、`data/conversation.json` に永続化。
- 毎ターン後に監視。生ログの概算トークン数が `CONVO_COMPRESS_TRIGGER_TOKENS`（既定1400）超、またはメッセージ数が `keep×2+4`（既定12）超で自動圧縮。
- 自動圧縮：直近 `CONVO_KEEP_RECENT_TURNS`（既定4）ターンを生で残し、それより古い部分を要約モデルで1つの要約に畳む（既存要約があれば統合）。恒常的事実は RAG へ移送。
- **手動の緊急圧縮**：GUIボタンで閾値を無視して即時実行。直近1ターンだけ残す。
- 画面のトランスクリプトは全件表示のまま。圧縮するのはモデルに送る中身のみ。

### 4.4 管理画面（GUI, `/admin`）

- Ollama の死活（稼働中 / 応答遅延 / 停止）、応答レイテンシ、ロード中モデルと VRAM 使用量を表示。5秒ごと自動更新。
- ワンクリック再起動。サーバー側で PowerShell を実行し、**Ollama プロセスツリー全体**（`ollama` + `llama-server` 等）を落として復帰させる（子プロセスの取り残し＝VRAMリークを防ぐため）。
- 緊急圧縮ボタン、会話リセット、長期知識の全消去。

### 4.5 リモートアクセス・認証

- Tailscale 経由でスマホからアクセスする前提。dev/本番とも `0.0.0.0` バインド。
- 共有パスワード1つ（`APP_PASSWORD`）。`src/proxy.ts`（Next.js 16 の `middleware` 改名版）で `/login` と `/api/auth/login` 以外を保護。ページは `/login` へリダイレクト、API は 401。
- 認証成功で HttpOnly Cookie（30日）。Cookie に `Secure` は付けない（Tailnet限定前提）。ユーザー管理はしない。
- レスポンシブ対応。

### 4.6 AI理解補助ビジュアライゼーション

- **目的**：非力なGPUで生成が遅い時間を、パイプラインの仕組みを図で学び、手で回して遊べる時間に変える。体感待ち時間の短縮。
- **表現**：6モジュール（入力→ベクトル化→検索→プロンプト構成→応答生成→出力）を左→右に配置。各モジュールは「その処理が実際に何をしているか」の3D図解。3Blue1Brown の図解から着想を得た方針で描く——少ない正確なオブジェクト、その場に置いたラベル、一貫した色分け、意味を担う幾何。これらは動画を見て得た解釈であり、先方が手法として公開しているものではない。色の割り当て（青＝流れるデータ／緑＝計算結果／橙＝保存済み／水色＝実行中）は本アプリ独自。
- **ニューロン演出**（光が層を走る）は、実際にNN推論する **ベクトル化と応答生成の2モジュールだけ**。他は固有の図（検索＝コサイン類似度の円錐、プロンプト＝文脈枠に部品が合流、生成＝次トークン確率の棒→選択→末尾へ追加＝自己回帰、など）。
- **カメラ**：既定は実行中モジュールに寄った状態。ステップが進むと次モジュールへ寄る。ユーザーはドラッグで回転・ピンチで拡大、タップで任意モジュールへ、ボタンで俯瞰。
- **同期**：`/api/chat` の NDJSON 進捗と連動。チャット中はローディング表示として、`/viz` では単体の展示モードとして。他機能に依存しない。実装は `src/components/NeuralViz.tsx`（Babylon.js、`next/dynamic` で必要時のみロード）。

### 4.7 アプリ内説明書（`/manual`）

- 6工程・RAG・自動圧縮・画面・触ってはいけない設定・起動手順・既知の制約を記載。
- 「現在の設定」表と本文中の数値は、パイプラインが使うのと同じ設定オブジェクト（`ollamaConfig` / `knowledgeConfig` / `conversationConfig` 等）から読む。手書きコピーのようにズレない。

## 5. モデルの役割分担

| 役割 | モデル | 制約・理由 |
|---|---|---|
| 応答生成 | `qwen3.5:9b` | やや賢め。日本語良好。`num_ctx=4096` 必須（後述）。`think=false` 必須（後述） |
| 要約 | `qwen3.5:2b` | 速度重視の軽量。文脈圧縮と事実抽出に使う |
| 埋め込み | `bge-m3` | 1024次元、多言語。RAG の検索・保存に使う |

**必須の設定制約（8GB VRAM 環境での実測に基づく）：**

- `OLLAMA_CHAT_NUM_CTX=4096`。Ollama 既定の 16384 では `qwen3.5:9b` が VRAM から溢れて 12% が CPU に落ち、22 tok/s が 13 tok/s に低下する。4096 なら 100% GPU。
- `OLLAMA_CHAT_THINK=false`。qwen3.5 は思考モデルで、有効だと思考だけでトークン予算を使い切り、空の応答が約50秒かけて返る。
- 3モデルの同時常駐は 8GB では不可。Ollama が keep-alive でスワップする（その回だけ待ちが伸びる）。詰まる場合は応答生成を 4B 級へ落として同居させる案がある。

## 6. 技術スタック

- **フレームワーク**：Next.js 16（App Router / `src/` / Turbopack）
- **ランタイム**：Node.js 24 / npm
- **言語**：TypeScript
- **スタイル**：Tailwind CSS v4
- **LLM実行**：Ollama（REST `/api/chat`・`/api/embed`）
- **ベクトルDB**：LanceDB（`@lancedb/lancedb`、アプリ内蔵）
- **可視化**：Babylon.js（`@babylonjs/core`）
- **リモート**：Tailscale
- **認証**：共有パスワード＋Web Crypto の Cookie トークン（外部ライブラリなし）

## 7. 非機能要件（実装済み）

- Ollama 停止時もクラッシュせずエラーメッセージ表示。`/api/ollama/health` を20秒ポーリングして「未接続」バナーを出し、`/admin` の再起動へ誘導。
- 一過性の失敗（`ECONNRESET` / `fetch failed` / タイムアウト / 5xx）は最大2回リトライ（`src/lib/retry.ts`）。
- モデルが空応答を返したらもう一度だけ生成し直す。ベクトル検索が失敗しても RAG なしで続行。
- ルートエラーバウンダリ（`src/app/error.tsx`）で真っ白画面を防ぐ。
- Tailnet 外からの不正アクセスを共有パスワードで防ぐ。

## 8. スコープ外・未実装

- クラウドLLM（外部API）連携
- マルチユーザー対応・ユーザー管理
- 画像・音声などマルチモーダル入力
- **応答のストリーミング表示**（生成完了まで本文が出ない。体感速度の最大の改善余地）
- **長期知識の個別削除**（全消去のみ）
- **複数会話スレッド**（会話は常に1本）
- **同時送信のガード**（2画面から同時送信で履歴が競合しうる）
- 正確なトークナイザ（圧縮の発火判定は文字数ベースの概算）
