# 技術調査結果

> 2026-09-01 改訂。構想時の OSS 比較に、実装で検証した結果と、実装中に判明した運用上の落とし穴を追記したもの。
> 「事前調査」と「作ってみて分かったこと」を分けて残している。

## 1. Ollama API / TypeScript連携

**事前調査：** Ollama は `http://localhost:11434` で REST を公開。`/api/chat` でチャット、`stream:true` で逐次。OpenAI互換API（`/v1/chat/completions`）もあり `openai` パッケージの `baseURL` を向けるだけで流用可。公式 `ollama` npm は型定義つき。埋め込みも同一サーバー（`/api/embed`）。応答生成・要約・埋め込みを単一プロセスでまかなえる（モデルだけ切り替え）。

**実装で採用：**
- `/api/chat` を **非ストリーミング**（`stream:false`）で使用。素の `fetch` で十分だったため公式パッケージも OpenAI 互換も使わなかった。
- 進捗表示は **Ollama のストリーミングではなく、自前の API ルートから NDJSON** を返す方式（1行1イベント：`{type:"stage",stage,status,ms,detail}` → `{type:"done"|"error"}`）。ステージごとの実処理を `await` の前後で計測している。
- 埋め込みは `/api/embed`（`{model, input}` → `{embeddings:[[...]]}`）。
- 思考モデル対策として `/api/chat` に `think` を渡している（後述）。

## 2. ベクトルDB（RAG用）の選定

| 製品 | 特徴 | 判定 |
|---|---|---|
| **LanceDB** | Rust製、アプリプロセス内で動く。別サーバー不要、ファイルに永続化。`@lancedb/lancedb` を公式提供 | ◎ 採用 |
| Chroma | APIは平易だが Python 中心、別サーバー前提 | △ |
| Qdrant / pgvector | 大規模向け。別サーバー or PostgreSQL 前提 | △ 個人利用にはオーバースペック |

「1台の自宅PCで完結し、管理対象のプロセスを増やしたくない」要件に対し、embedded 型の LanceDB が最適。

**実装で判明した注意点：**
- Next.js（App Router）は route handler の依存を既定でバンドルする。LanceDB はネイティブアドオンなので `next.config.ts` の `serverExternalPackages: ["@lancedb/lancedb"]` が必要。
- `@lancedb/lancedb` の peer に `@types/node >=22`。プロジェクトを `^24` に上げた。
- `npm audit` が `sharp` の脆弱性を high で報告する。経路は `@lancedb/lancedb` → `@huggingface/transformers` → `sharp`。これは transformers.js のローカル埋め込み／画像処理用で**本アプリでは未使用**（埋め込みは Ollama）。`audit fix` は LanceDB を破壊的にダウングレードするため見送り。
- テーブルはスキーマを手書きせず、初回挿入で遅延作成している。
- 距離は cosine。しきい値 `0.75`、上位 `3` 件（`src/lib/knowledge.ts` の `TOP_K` / `MAX_DISTANCE`）。

## 3. モデル選定（軽量帯）

**事前調査：** 2026年8月時点の軽量帯候補は Qwen3系（多言語・日本語に定評、RAG用途で多用）／Gemma 3・4（英語は強いが小サイズだと日本語の自然さが劣る）／Llama 3.2 3B（汎用バランス）／Phi-4 Mini。要約・埋め込みは 1B 前後、応答生成はもう一段大きめ、が現実的。VRAM量を見て実機で試す。

**実装で採用：** 応答生成 `qwen3.5:9b` ／ 要約 `qwen3.5:2b` ／ 埋め込み `bge-m3`（1024次元）。

**実機（8GB Radeon RX Vega / Vulkan）での実測——ここが一番重要：**

| 項目 | 結果 |
|---|---|
| `qwen3.5:9b` @ `num_ctx=16384`（Ollama既定） | フットプリント 6.6GB、`12%/88% CPU/GPU` に分割、**約13 tok/s** |
| `qwen3.5:9b` @ `num_ctx=4096` | フットプリント 5.5GB、**100% GPU、約22 tok/s** |
| → **結論** | 8GB GPU では chat モデルの `num_ctx` を明示的に絞らないと CPU に溢れる。`options.num_ctx` を必ず指定する |

**思考モデルの罠：** `qwen3.5` は reasoning モデル。`think` を有効のまま使うと、思考（`<think>`）だけでトークン予算を使い切り、`message.content` が空で返る。しかも約50秒かかる。**chat には `think:false` を必ず指定**。速度が要る要約用途でも同様。

**同時常駐：** 8GB では chat(9b) + summary(2b) + embed の同時ロードは不可。Ollama が keep-alive でスワップする前提（圧縮が走る回だけ待ちが伸びる）。RAM は物理16GBで空きが少ないため、CPU フォールバックは避け、GPU に載る `num_ctx` を維持する。

## 4. Tailscale を使った外部アクセス

**事前調査：** WireGuard ベースのメッシュVPN。ポート開放不要で自宅PCとスマホを同一プライベートネットワークに入れられる。アプリは localhost バインドのまま `Tailscale Serve` でプロキシするのが推奨。同一Tailnet内のみの公開なら追加認証なしでもある程度安全だが、Tailscale のユーザー識別ヘッダーやアプリ側の簡易パスワードを併用するのが望ましい。Funnel（公開インターネット露出）は個人用管理画面には不要。

**実装で採用：** dev/本番とも `-H 0.0.0.0` でバインドし、Tailnet から `http://<Tailscaleホスト名>:3000` / `http://<TailscaleのIP>:3000` で到達。Tailscale Serve は使っていない（素のHTTP）。アプリ側で共有パスワード認証を実装。Cookie に `Secure` を付けていないのは Tailnet 限定・素のHTTP前提での割り切り。

## 5. 実装中に発見した運用上の落とし穴

以下は事前調査では出てこず、作って初めて分かったもの。継ぐ人はここを読んでおくと詰まらない。

### 5.1 Ollama 再起動と VRAM リーク（最重要）

`ollama.exe` だけを force-kill すると、子プロセスの `llama-server.exe`（モデル実行ワーカー）が**オーファン化して VRAM を掴んだまま残る**。次のモデルロードが 8GB GPU で確実に OOM する（`ggml_vulkan: ... ErrorOutOfDeviceMemory` / `failed to allocate Vulkan0 buffer`）。

→ 再起動コマンドは **`ollama` + `llama-server` + `ollama_llama_server` をまとめて kill** する。tray アプリ（`ollama app`）は残してクリーンに再スポーンさせる。管理画面の再起動はこれを実装済み。手動なら：

```powershell
Get-Process ollama,llama-server -EA SilentlyContinue | Stop-Process -Force
```

### 5.2 OneDrive とビルド

プロジェクトが OneDrive 配下にあると、`next build` が `.next` 内のファイル削除で `EPERM`（OneDrive がロック）で落ちることがある。→ サーバーを止めて `.next` を消してからビルドすれば通る。`node_modules` の同期も遅いので `npm install` 時は OneDrive を一時停止すると安定。

### 5.3 Windows シェルと日本語

Git Bash / PowerShell から `curl -d '{"message":"日本語"}'` を投げると文字化けする。API の動作確認は**ブラウザ経由**で行うこと。

### 5.4 Next.js 16 の破壊的変更

- `middleware.ts` → `proxy.ts` に改名（export 名も `middleware` → `proxy`）。
- route handler の細部が変わっているため、書く前に `node_modules/next/dist/docs/` の該当ガイドを見る習慣（`AGENTS.md` にも記載）。

### 5.5 Babylon.js のツリーシェイキング

`@babylonjs/core` を個別 import する構成では、`scene.createPickingRay()` が `Ray needs to be imported before as it contains a side-effect` で例外を投げる。→ ピッキングは `Vector3.Project` で各対象を画面座標に投影して最寄りを選ぶ方式にすれば `Ray` 依存を避けられる。

## 6. まとめ・推奨構成

- **バック／フロント**：Next.js 16（Node.js 24）＋ Ollama（REST）
- **ベクトルDB**：LanceDB（embedded、`serverExternalPackages` 指定）
- **モデル**：応答 `qwen3.5:9b`（`num_ctx=4096`, `think=false`）／要約 `qwen3.5:2b`／埋め込み `bge-m3`
- **可視化**：Babylon.js（`@babylonjs/core`、動的 import）
- **リモート**：Tailscale（`0.0.0.0` バインド＋アプリ側パスワード）

Python 環境を一切必要とせず、TypeScript / Node.js のみでワークフロー型ローカルLLMアプリを完結できることを実装で確認した。
